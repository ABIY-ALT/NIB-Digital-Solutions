# AppCore — NIB application framework

AppCore is the shared foundation for NIB digital products. Phase 1 delivers the
base architecture plus end-to-end authentication and authorization.

```
appcore/
├── backend/     NestJS 12 API — Clean Architecture, PostgreSQL (Prisma 7), Redis
├── frontend/    Next.js 16 UI + Backend-for-Frontend (BFF)
├── contracts/   openapi.json — the shared API contract (generated by the backend)
└── tools/       generator/ — the feature generator (npm run generate)
                 cli/ — the workspace CLI (npm run appcore)
```

Workspace scripts (root `package.json`, no monorepo tooling):

| Command | What it does |
|---|---|
| `npm run generate -- feature <name> --fields "…"` | Scaffolds a complete feature (see *Feature generator*) |
| `npm run appcore -- setup` | First-time setup: environment files with matching secrets, dependencies, database (see *Command line*) |
| `npm run appcore -- doctor` | Checks both projects: configuration, shared secrets, database, translations, routes, contract |
| `npm run contract` | Backend → `contracts/openapi.json` → frontend types |
| `npm run check` | Generator tests, then backend and frontend checks (types, lint, format, tests, contract drift) |

## Request flow

```
Browser component ──► TanStack Query hook ──► Next.js API route (/api/*) ──► NestJS API (/api/v1/*)
                                               │  encrypted httpOnly session     │  HMAC service identity
                                               │  CSRF + Origin check            │  AES-256-GCM payload encryption
                                               │  token refresh (proxy.ts)       │  JWT + session check, RBAC/ABAC
```

The browser never sees a token. It holds an encrypted, httpOnly session cookie.
The BFF signs every backend call with its own service identity and can encrypt the payload.

## Run locally (no Docker)

Prerequisites: Node.js 24+, PostgreSQL running locally with database `appcore`,
user `postgres`, password `User@123456`. Redis is optional in development
(`KV_STORE=memory`).

```bash
# 1. Backend  → http://localhost:4000  (Swagger: http://localhost:4000/docs)
cd backend
npm install
cp .env.example .env            # then paste secrets from: npm run keys:generate
npx prisma migrate deploy
npm run db:seed
npm run start:dev

# 2. Frontend → http://localhost:3000
cd ../frontend
npm install
cp .env.example .env.local      # shared secrets must match the backend .env
npm run dev
```

With Docker, `docker compose up -d` in `backend/` starts PostgreSQL 18 and Redis 8. Set `KV_STORE=redis` in that case.

`npm run dev` uses the webpack dev server. The VS Code extension **Console Ninja** patches Next.js and truncates the JavaScript served by the Turbopack dev server. With Turbopack the page renders but nothing is interactive. If you disable Console Ninja for this workspace, you can use `npm run dev:turbo` instead.

Guard rails on roles and accounts:
- **Grants.** You can grant only permissions you hold yourself, so there is no privilege escalation. Attempts are denied and audited.
- **System roles.** They cannot be renamed or deleted, and the super role (`*`) keeps its permissions. A role that is still assigned to users cannot be deleted.
- **Password changes.**
  - Your own change needs your current password and signs out your other sessions.
  - An admin reset signs the user out everywhere, and you cannot reset your own password this way.
- **Turning MFA off** needs the password. A new authenticator is enabled only after you enter a valid code from it.

## Enterprise controls

### Maker–checker (four-eyes) approvals

Sensitive changes take effect only after a **second, entitled person** approves them.

- **Configuration only.** `APPROVAL_ACTIONS` lists the actions under four-eyes control (default `roles.create,roles.update,roles.delete,users.delete`; also available: `users.update`, `reference-data.items.create|update|delete`, and every generated feature's `<feature>.create|update|delete`). `APPROVALS_ENABLED=false` switches it off; `APPROVAL_EXPIRY_HOURS` sets the deadline.
- **Flow.** The maker's request is validated immediately (the same checks as a direct change), stored with a before/after snapshot and an optional reason (`X-Change-Reason`), and the API answers **202 Accepted** with an approval ticket. Entitled checkers are notified.
- **Rules.** The maker can never decide their own request; checkers need `approvals:approve` plus the permission of the action; rejection needs a reason; a request expires automatically. On approval the change is applied with the **maker's current authority**. If the record changed meanwhile (optimistic concurrency) or the maker lost the permission, the request becomes **FAILED** instead of being applied.
- **Evidence.** `*_REQUESTED`, `APPROVAL_APPROVE/REJECT/CANCEL` and `APPROVAL_APPLIED` audit records, plus the retained request itself.
- **For developers.** A feature registers an `ApprovalHandler` (`describe` + `execute`) and routes its write through `APPROVAL_GATE`; the controller returns `this.gated(outcome, toDto)`. In the UI, `<ApprovalNotice action="…">` asks for the reason when (and only when) the policy requires approval, `useSaveFeedback()` says "Saved" or "Submitted for approval", and `usePendingApprovals()` marks rows with a pending change.

Demo: sign in as **admin**, edit a role (→ submitted); sign in as **useradmin** → *Approvals* → approve.

### Notifications

In-app inbox per user (Gmail-style: Inbox, Unread, Starred, Archive, Trash, All; category labels; bulk and hover actions; search; reading pane; keyboard shortcuts `j/k/o/u/e/#/s/?`), a header bell with live unread count, per-category channel settings (in-app, e-mail; security alerts cannot be muted) and announcements to everyone or selected roles.

Features never call each other: they publish **application events** (`core/application/events/app-events.ts`: approval submitted/decided, password changed/reset/expiring, account locked, new sign-in, session evicted, MFA changed/required) and the notifications module turns them into messages. Messages store a template id and parameters, so the UI shows them in the reader's language. E-mail uses the `MAIL_TRANSPORT` port (the default development transport logs the message; bind SMTP or a provider in production). Any feature can also inject `NOTIFIER` directly.

### Account security policies

All configurable through environment variables (see `backend/.env.example`) and visible to auditors under *Security & compliance → Policies*:

| Policy | Variables (defaults) |
|---|---|
| Password composition | `PASSWORD_MIN_LENGTH=10`, `PASSWORD_REQUIRE_UPPERCASE/LOWERCASE/DIGIT/SYMBOL=true`; names, usernames and common passwords are always refused |
| Reuse and age | `PASSWORD_HISTORY_COUNT=5`, `PASSWORD_MAX_AGE_DAYS=90`, `PASSWORD_MIN_AGE_HOURS=0`, `PASSWORD_EXPIRY_WARNING_DAYS=14` |
| Temporary passwords | `PASSWORD_CHANGE_ON_FIRST_LOGIN=true`: passwords set by an administrator (new users, resets) must be replaced at the next sign-in |
| Sessions | `SESSION_MAX_CONCURRENT=3` (oldest session ends), `NEW_DEVICE_ALERTS=true`, idle timeout and lockout as before |
| Two-step verification | `MFA_REQUIRED_ROLES=` (e.g. `SUPER_ADMIN,ADMIN`): members are reminded until they enrol |

The same rules drive the live checklist in every password form (sign-in change, profile, administrator reset, new user) through `GET /auth/password-policy`; violations come back per rule (`code`) and are shown translated.

### Tamper-evident audit trail and data retention

- **Hash chain.** Every audit record is sealed: `hash = HMAC-SHA256(AUDIT_CHAIN_KEY, previous hash | canonical record)`. Changing, deleting or reordering any record breaks the chain; without the key nobody can recompute it.
- **Database guard.** A trigger rejects `UPDATE`, `DELETE` and `TRUNCATE` on `audit_logs`, except sealing a row once and purges run by the retention job.
- **Anchors.** A daily job records the chain head (`audit_checkpoints`), so deleting the newest records is detected too.
- **Verification.** *Security & compliance → Audit integrity → Verify now* recomputes every link and reports the first broken record. The verification itself is audited.
- **Retention.** Each module registers a policy (audit trail 7 years, approval requests 2 years, notifications 6 months; `*_RETENTION_DAYS`). The retention job runs every `RETENTION_INTERVAL_HOURS`, archives where required (JSON Lines + SHA-256 manifest under `ARCHIVE_DIR`; bind `ARCHIVE_STORAGE` to WORM object storage in production), purges in batches, writes a PURGE checkpoint so the remaining chain still verifies, and records the run. Dry runs show what would be removed.
- **Key management.** Set a dedicated `AUDIT_CHAIN_KEY` (`npm run keys:generate`); production refuses to start without it. **Changing the key invalidates existing seals.** Record an anchor and archive the trail before a planned key change, and keep old keys for verifying archives.

Background jobs (retention, approval expiry, chain anchors, password-expiry reminders) run on one instance at a time through a lock in the key/value store; *Security & compliance → Background jobs* shows their status and can run them now. `JOBS_ENABLED=false` disables them.

### Shared API contract

The backend is the source of truth. Response DTOs are Zod schemas registered with `apiSchema('Role', …)`; they type the controller, appear as named OpenAPI components, and are exported without starting the server:

```
backend  npm run contract:export  → contracts/openapi.json      (npm run contract:check fails in CI when stale)
frontend npm run api:generate     → src/shared/api/contract.gen.ts (npm run api:check, part of npm run check)
```

The frontend aliases the generated types (`export type Role = ApiSchemas['Role']`) and types BFF calls with `ApiData<'GET /roles/{id}'>`; the error-code catalogue is generated too. A backend change the UI does not follow is a compile error, not a production bug. (The generator is dependency-free because `openapi-typescript` does not yet support TypeScript 6.)

### Reference data

Managed code lists (currencies, countries, regions, branches, ID document types, account types are seeded). Each list declares the **extra attributes** its items carry (text, number, yes/no, date, choice), items have translations (`labels.am`), a display order, validity dates, activation and an optional parent (branch → region). Codes are permanent (never reused). The cached lookup API returns effective items in the reader's language; in forms use `<ReferenceSelectField type="branches" />` or `useLookup('currencies', { parent })`. The user form's branch field and the users branch filter already do.

### Feature generator

```bash
npm run generate -- feature loan-products --label "Loan products" --icon Wallet \
  --fields "code:string:required:unique,name:string:required,rate:number:required,maxTermMonths:int,active:boolean,launchedOn:date,notes:text"
```

Field types: `string`, `text`, `int`, `number`, `boolean`, `date`; flags `required`, `unique`. One command creates and wires:

- **Backend:** Prisma model, entity with validation, repository port and Prisma implementation (sort/filter/search spec), use cases, maker–checker handlers, controller with contract DTO, audit and permissions, module, entity spec, `app.module` registration, seed permissions.
- **Frontend:** types from the contract, resource, form schema, BFF routes (CRUD + CSV/Excel export), hooks, list page (search, sort, export, row actions, pending-approval badges), form dialog (with the approval reason), i18n (en/am), page and route files, navigation entry.
- **Contract:** runs `prisma generate`, exports the contract and regenerates the frontend types, then formats everything.

Then create the migration (`npx prisma migrate dev --name add_loan_products`), seed permissions, restart. `npm run generate -- remove loan-products` undoes a generation (files and every registration). Options: `--dry-run`, `--force`, `--skip-build`. Generated code passes typecheck, lint and its spec unchanged; it is a starting point to extend like hand-written code.

### Audit log: previous and new values

- **What is recorded.** Every create, update, delete or restore through a `PrismaBaseRepository` inside a request records each changed field's old and new value.
  - The changes are stored as `metadata.changes` on the request's `DATA_CHANGE`, `SECURITY` or `FINANCIAL` record, so the hash chain seals them too.
  - Bookkeeping columns (`version`, `updatedAt`, …) are left out, and a failed request records no changes.
  - Secrets (`passwordHash`, `mfaSecret`, anything named like password, secret, token, pin or otp) are only marked *changed*; their values are never stored.
  - Maker–checker requests record the *proposed* values. The approval, when applied, records the real ones.
- **Extending it.** A repository can add related data to the audited view with `auditSnapshot()`: roles add `permissions`, users add `roles`. It can also redact or ignore more fields with `auditDiff`.
- **The page** (`/audit`) follows the IB audit log:
  - An activity strip (events, distinct users, failures, top actions) whose tiles act as filters.
  - Time windows and filters for outcome, category, action, resource type, username, IP and date.
  - A detail modal (`?id=`) with previous → new values, actor and session, request and outcome, client and location, and cross-references (correlation ID, chain position).
- **API:** `GET /audit-logs/:id`, `/audit-logs/activity`, `/audit-logs/facets`.

### Themes (light, dark, system)

- **Where users choose.** A header switcher (also on the sign-in card), *My profile → Preferences → Appearance*, and quick search ("dark theme").
- **Configuration** in `app.config.ts`:
  - `theme.mode` is the default colour mode.
  - The `darkMode` feature controls whether users may change it.
  - `theme.darkColors` optionally sets the dark-mode brand colours.
  - `theme.tokens.light` / `theme.tokens.dark` override any semantic token (neutrals, status, charts) per mode.
- **How the palettes are built.** Both palettes come from the same config (`themeToCss`). Dark brand colours are lightened automatically to keep WCAG AA contrast. Solid status fills use `*-foreground` tokens, like `primary-foreground`.
- **Components** style with semantic tokens only (`bg-surface`, `text-muted-foreground`, …), so they work in both modes without `dark:` variants.
- **No flash of the wrong palette.**
  - The choice is kept in the `appcore.color-mode` cookie (not sensitive), so the server renders the right palette on the first paint.
  - "System" uses the `Sec-CH-Prefers-Color-Scheme` client hint when the browser sends it. Otherwise a small pre-paint script, allowed by the page's per-request CSP nonce, applies it.
  - Tabs stay in sync, and system changes are followed live.
- **In code:** `useTheme()` returns `{ mode, resolved, setMode, canSwitch }`.

### Quick search (Ctrl K / ⌘K or "/")

- **One box** to open any page, sub-page (profile tabs, compliance tabs, filtered views), action (theme, language, change password, sign out) or record the user may access.
- **Pages and actions** are matched in the browser by `shared/lib/fuzzy.ts`:
  - It handles prefixes, acronyms ("rd" → Reference data), abbreviations, one typo ("pasword") and Amharic.
  - Matched characters are highlighted, and weak matches are dropped when strong ones exist.
- **Records** come from one federated endpoint, `GET /api/search?q=`:
  - It searches only the modules the user may read, in parallel on the server.
  - Each source is limited and has its own time limit, so a slow module never breaks the others.
- **Recent items** keep only page and action IDs, never record names, per user and browser.
- **Extending it:**
  - Navigation items are searchable automatically, including generated features.
  - Add sub-pages to `features/quick-search/destinations.ts`.
  - Add a searchable module as a source in `features/quick-search/api/search.routes.ts`.
- **Reuse.** The dialog is the reusable `shared/ui/command-palette.tsx` (combobox, keyboard navigation, highlighting). The sidebar's menu filter uses the same fuzzy matcher.

### Command line

Three entry points with the same options, output rules and exit codes. Full reference: [docs/cli.md](docs/cli.md).

```bash
npm run appcore -- setup                       # appcore/: env files, install, migrate, seed
npm run appcore -- doctor                      # appcore/: is everything consistent?
cd backend  && npm run cli -- help             # operations (production: node dist/cli/main.js)
cd frontend && npm run cli -- help             # project checks and scaffolding
```

- **Backend CLI.** Runs the same use cases as the API, without the HTTP layer: `users:create`, `users:unlock`, `users:reset-password`, `permissions:sync`, `audit:verify`, `retention:run`, `jobs:run`, `config:check`, `db:status`, `routes:list` and more.
  - Every change is attributed to the operator and written to the audit trail as `CLI_*`, with field-level changes.
  - In production a change needs `--reason` and a confirmation. Actions under maker–checker control are refused unless `--break-glass` is given, and that is audited too.
  - `permissions:sync` and `users:create` bootstrap a new environment; the development seed refuses to run in production.
- **Frontend CLI.** `doctor`, `env:check` (also compares the shared secrets with the backend), `config:check`, `i18n:check`, `routes:list`, `make:page`.
- **Gates.** `config:check --production --strict` before deployment, `db:status` before switching traffic, `routes:list --check` in CI, `audit:verify` on a schedule. Exit code 2 means a check found a problem.

### Runtime settings

**Administration › Settings** (`/settings`, `settings:read` / `settings:manage`) holds what an administrator changes without a deployment: company details and logo, money and date formats, e-mail sender name and footer, document page size, accent colour and footer. Only values that differ from the default are stored (table `settings`); changes are validated, cached for 60 seconds across instances and recorded in the audit log with previous and new values.

A feature adds its own settings at startup and reads them anywhere. They appear in the screen without frontend work:

```ts
onModuleInit() {
  this.settings.define([{ key: 'loans.maxTenorMonths', group: 'loans', type: 'number', label: 'Longest tenor (months)', default: 60, min: 1 }]);
}
const tenor = await this.settings.number('loans.maxTenorMonths');   // @Inject(SETTINGS)
```

Settings marked `public` (company name, logo, formats) are readable by every signed-in user through `GET /settings/public`; the frontend hook `useFormats()` returns a `money()` formatter that follows them. Never store secrets in settings.

### E-mail

Inject `MAILER` to send a message in the product layout (HTML and text, sender name, reply-to and footer from the settings):

```ts
await this.mailer.send({ to, toName, subject: 'Statement ready', paragraphs: ['…'], action: { label: 'Open', url }, attachments });
```

`MAIL_TRANSPORT=log` (default) writes e-mails to the backend log, including the text outside production, so links can be followed without a mail server. `MAIL_TRANSPORT=smtp` sends through `SMTP_HOST` / `SMTP_PORT` (STARTTLS on 587, or `SMTP_SECURE=true` for 465), with optional `SMTP_USER` / `SMTP_PASSWORD`. For an internal relay whose certificate comes from a private CA, set `SMTP_TLS_REJECT_UNAUTHORIZED=false`. Notification e-mails use the same transport.

### Forgot password

"Forgot password?" on the sign-in card opens `/forgot-password`: the user enters a username or e-mail address and receives a link to `/reset-password` (`POST /auth/password/forgot`, `POST /auth/password/reset`).

- The answer is the same, and immediate, whether or not the account exists.
- The link is single use, expires after `PASSWORD_RESET_TTL_MINUTES` (30) and only its SHA-256 hash is stored. A new request invalidates the previous link, and at most one e-mail is sent per `PASSWORD_RESET_COOLDOWN_MINUTES` (2).
- The new password must meet the password policy, including history. Setting it ends every session of the account and lifts a temporary lock. No session is created: the user signs in afterwards, so MFA still applies.
- Disabled, administratively locked and SSO-only accounts cannot use it.

Turn it off with `PASSWORD_RESET_ENABLED=false` and by removing `app.links.forgotPassword` from `app.config.ts` (the link then shows the help-desk guidance again).

### Documents (PDF) and "send this record"

A module makes its records printable by registering a `DocumentSource` (see `modules/roles/application/role-document.source.ts`): it returns a `DocumentModel` (title, reference, summary fields, sections of fields, tables with totals, or text). The renderer (pdfkit, no browser) adds the company header and logo, formats money and dates per the settings, repeats table headers across pages and prints the footer with page numbers.

- `GET /documents/{source}/{id}/pdf` returns the PDF. The caller needs one of the source's permissions.
- `POST /documents/{source}/{id}/send` e-mails it as an attachment. This also needs `documents:send`, and the audit entry records the recipient.

On the frontend, `<DocumentActions source="roles" id={role.id} name={role.name} />` adds "Download PDF" and "Send by e-mail" (shown in the role detail view). The built-in font covers Latin text only; register a font with Ethiopic glyphs in the renderer to print Amharic.

### Line items (master–detail forms)

`<LineItemsField name="items" columns={…} newRow={…} summary={…} />` (`@/shared/ui/line-items-field`) edits an array field of a form as rows: text, number, select, computed and custom columns, add and remove with `minRows` / `maxRows`, per-cell validation messages from the Zod schema, and a totals block. Wide containers show a table; narrow ones stack each row as a card. Enter moves down a column and adds a row from the last one. `lineAmount()` and `lineTotals()` (`@/shared/lib/line-items`) compute quantity × price, discount, tax and total, rounded to the currency's decimals. A working example is on the Components page under **Forms**.

### Dashboard catalogue

Eight ready-made dashboards that a product switches on or off, modelled on common admin templates: **CRM**, **eCommerce**, **Analytics**, **Finance**, **Logistics**, **Support**, **Academy** and **People (HR)**. A hub at `/dashboards` lists the ones the user may open; each one lives at `/dashboards/{id}` and keeps its period in the URL (`?range=7d|30d|90d|12m`).

- **One registry.** `features/dashboards/registry.ts` lists each dashboard: icon, category, feature flag (`dashboards.<id>`), optional `requires` (permission or role), offered periods, default period and refresh interval. The page, the BFF route, the hub and the switcher all read it.
- **Configuration only.** In `app.config.ts`, set `features['dashboards.crm'] = false` to drop a dashboard: its menu entry, page and API route disappear (404). Reorder or remove entries in the `dashboards` navigation section.
- **Providers, not hard-coded data.** Every dashboard has one screen-shaped payload (`DashboardDataMap` in `types.ts`). On the server, `api/providers.ts` decides where it comes from. By default it is `sample(id)`: deterministic generated data, labelled *Sample data* in the UI. Switch a dashboard to real data by replacing its entry with `live(async ({ api, range }) => …)`. The provider calls the backend with the user's token, so every check still applies, and no view code changes.
- **Request flow.** View → `useDashboardData(id, range)` → `GET /api/dashboards/{id}?range=` → provider. The page prefetches the same query on the server, so the first paint has data. Changing the period keeps the old figures on screen until the new ones arrive.
- **Formatting.** `useDashboardFormat()` formats money in the product's currency (*Administration › Settings*). Numbers, dates, weekdays and country names follow the reader's language. All text is in `features/dashboards/i18n` (en, am).
- **Reusable widgets** (in `shared/ui/widgets` and `shared/ui/charts`, usable on any page): `WidgetCard`, `HeroCard`, `StatGrid` + `IconTile`, `EntityList`, `CompactTable`, `ProgressBar`, `DeltaBadge`, `MiniBars`, alongside the existing KPI cards, charts, gauges, funnels, timelines and trackers.

Adding a dashboard: add its payload type to `DashboardDataMap`, an entry to the registry, a provider and a view (both are mapped types, so a missing one is a compile error), messages under `dashboards.catalogue.<id>` and `dashboards.<id>`, and a flag plus navigation item in `app.config.ts`. `dashboards.spec.ts` checks that the registry, the providers, the configuration and the translations agree.

## CI/CD and deployment

The GitLab pipeline (`.gitlab-ci.yml`) is NibTera's DevSecOps pipeline. It builds and smoke-tests the images on every push, and pushes them as candidates only. Merge requests into `dev`, `staging` and `main`, and pushes to `dev` and `staging`, must pass lint and tests, SonarQube, SAST, secret detection, the npm audit gate, a migration check, Trivy and Snyk; the image checks run the candidates by digest. Only then do pushes to `dev` and `staging` promote the candidates, unchanged, to their release tags (`.release/promote.sh`), and pushes to `staging` deploy that release by digest. Setup, rollback and the reasoning behind each gate: [docs/ci-cd-recommendations.md](docs/ci-cd-recommendations.md).

| File | What it is |
|---|---|
| `backend/Dockerfile`, `frontend/Dockerfile` | Production images: backend, `backend-migrate` (`--target migrate`), frontend (Next.js standalone) |
| `docker-compose.local.yml` | The three images plus Redis on this machine, against your PostgreSQL: `docker compose -f docker-compose.local.yml up -d --build` |
| `docker-compose.staging.yml` | What `deploy_staging` runs on the staging server; secrets come from `backend/.env.staging` and `frontend/.env.staging` (templates: `*.env.staging.example`) |
| `.security-gate/`, `.npm-audit/` | The gates' scripts and waivers, each with an expiry date and a reason |
| `.release/promote.sh` | Checks every gate's evidence and copies the validated candidates, by digest, to `:<sha>` and `:dev` or `:staging`: the only writer of release tags |
| `renovate.json` | Dependency and image updates, as merge requests into `dev` |

## Version notes (principle 11)

All packages use the latest stable release, with three documented exceptions:

- **Prisma 7.10 (not 8.0).** npm's `latest` tag points to `8.0.0-rc`, which is a release candidate.
- **TypeScript 6.0 (not 7.0).** The NestJS 12 CLI requires TypeScript 6. TypeScript 7 is the new native compiler, and its programmatic API is not yet supported by the tooling.
- **Auth.js v5 (`next-auth@5.0.0-beta.32`).** npm publishes the App Router line only under the beta tag. The `latest` tag is still the legacy NextAuth v4.

## Structural decisions

- **The frontend is a single Next.js project, not a Turborepo monorepo.** This was the product owner's decision. Framework code lives in `src/shared` (UI kit, layouts) and `src/infrastructure` (config, API client, security, logging). Features are self-contained in `src/features/<feature>`.
- **Redis is optional in development.** All Redis usage goes through a `KeyValueStore` interface, and `KV_STORE=memory` runs without Redis. Production validation refuses the memory store.
